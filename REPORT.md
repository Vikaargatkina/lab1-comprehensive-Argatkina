# Итоговый аналитический отчет (Лабораторная работа №1)

## 1. Резюме (Executive Summary)
В рамках лабораторной работы №1 спроектирован с нуля процесс разработки, контроля версий и автоматизированного контроля качества для нового микросервиса «Расчет корзины и скидок» системы лояльности. Выбрана оптимальная СУБД для хранения финансовых транзакций и бонусных баллов, настроена защита веток в GitHub, внедрен CI-пайплайн с линтером `flake8`, проведено обратное проектирование legacy-алгоритма расчета скидок и составлен регламент проведения code-review.

### 2.1. Матрица принятия решений

| Критерий выбора | Вес | PostgreSQL (балл) | PostgreSQL (взвеш.) | MongoDB (балл) | MongoDB (взвеш.) |
| :--- | :---: | :---: | :---: | :---: | :---: |

### 2.2. Расчет и обоснование выбора
Расчет взвешенной оценки выполнен по формуле:  
`Оценка = Сумма (Вес_критерия * Балл_кандидата)`

* **PostgreSQL:** `0.35 * 5 + 0.25 * 5 + 0.20 * 5 + 0.10 * 3 + 0.10 * 4 = 1.75 + 1.25 + 1.00 + 0.30 + 0.40 = 4.70`
* **MongoDB:** `0.35 * 3 + 0.25 * 3 + 0.20 * 3 + 0.10 * 5 + 0.10 * 4 = 1.05 + 0.75 + 0.60 + 0.50 + 0.40 = 3.30`

**Вывод:** Победителем выбрана реляционная СУБД **PostgreSQL** (4.70 балла против 3.30). Для микросервиса расчета корзины, скидок и начисления бонусных баллов критически важна строгая гарантия ACID-транзакций и ссылочная целостность финансовых операций, где PostgreSQL значительно превосходит документоориентированную MongoDB.

## 5. Обратное проектирование и планирование ревью

### 5.1. Анализ алгоритма
<img width="1076" height="1196" alt="uml_diagram" src="https://github.com/user-attachments/assets/3212b255-94d0-4b52-8a30-204182e0ce31" />


**Выявленные «запахи кода» (Code Smells) в legacy-фрагменте `calculate_cart_total`:**
* **Магические числа (Magic Numbers):** В коде жестко зашиты константы (`15000`, `0.85`, `500`, `0.90`, `0.97`, `0.93`, `0.70`) без вынесения в именованные константы или конфигурацию.
* **Отсутствие валидации входных данных:** Нет проверок на отрицательную сумму корзины (`cart_sum < 0`), некорректный уровень лояльности (`tier`) или тип данных `promos`.
* **Использование `float` для денежных расчетов:** Применение чисел с плавающей точкой вместо `Decimal` может приводить к ошибкам округления финансовых сумм.
* **Дублирование промокодов в цикле:** Если в списке `promos` передать `["SUMMER", "SUMMER"]`, скидка применится несколько раз, что создает риск финансового фрода.
* **Высокая цикломатическая сложность:** Вся логика расчета скидок, промокодов и ограничений смешана в одной функции вместо разбиения на отдельные функции или паттерн «Стратегия».

### 5.2. План code-review
Для модуля `src/discount.py` разработан регламент проведения инспекции кода в файле `docs/review-plan.md`.  
https://github.com/Vikaargatkina/lab1-comprehensive-Argatkina/pull/3



* **Ключевые измеримые критерии:** отсутствие магических чисел, покрытие модульными тестами (unit-tests) более 80%, обязательная валидация входных параметров, прохождение `flake8` без предупреждений.
* **Механизм эскалации:** при возникновении разногласий между автором кода и ревьюером спорный вопрос выносится на обсуждение с Tech Lead / архитектором проекта в комментариях к PR; если решение не принято в течение 24 часов, финальное решение принимает Tech Lead на основе требований безопасности и бизнес-логики.



## 6. Заключение
Внедренные инженерные практики (защита основной ветки, обязательное code-review через CODEOWNERS и автоматический статический анализ через GitHub Actions) позволяют блокировать попадание некачественного кода в основную ветку на раннем этапе. Проведенный реверс-инжиниринг legacy-алгоритма выявил критические уязвимости в расчете скидок (возможность многократного применения промокодов и отсутствие валидации), которые будут устранены при рефакторинге согласно утвержденному плану ревью.
